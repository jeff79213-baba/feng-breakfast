# 風自然餐廳專用 — 早餐生產規劃系統 設計規格

日期：2026-10-04
專案：風自然餐廳專用（全新專案，目錄原為空）
Firebase 專案：`opencode-sk`（沿用）／Hosting Site：`fzbf-sk`／Functions：`fzapi`

---

## 1. 背景與目標

餐廳有一館、二館兩個館，必須在每天早上前決定「今天要出哪些菜、水果、甜點，飯粥蛋要準備多少份，牛奶飲料要補多少」。目前靠人工手寫、口頭交班，容易漏、不好回頭查。

本專案目標：

1. 多裝置共用資料，員工用手機就能查、就能改
2. 主帳號可建立／停用／刪除員工帳號（處理離職）
3. 依當日房間數自動算出**參考**菜色道數與水果甜點種數，人工以勾選決定實際要出什麼
4. 可預先輸入連續 7 天的內容
5. 冰箱庫存生鮮勾選，讓採買人員知道要補哪些菜
6. 可匯出 CSV

### 1.1 來源專案

`房號與早餐` 的「備料區」（`index.html` 備料區 modal、`app.js` `calcPrep()`）計算公式與 UI 模式被沿用，作為本專案備料區的基礎。差異：

| 項目 | 房號與早餐 | 本專案 |
|---|---|---|
| 計算對象 | 單日住客清單 | 單日 × 三個目標（一館／二館／合計） |
| 備料項目 | 果凍奶酪、茶葉蛋、主食 | 飯、粥、茶葉蛋 |
| 額外增加 | 無 | 每項都有手填「額外增加」欄 |
| 儲存 | localStorage | Firestore |
| 權限 | 無 | 登入 + 主帳號／員工 |

## 2. 已確認的需求決策

### 2.1 入住統計

- 手動輸入**一館**與**二館**各自的：房間數、大人、小孩、嬰幼兒
- 合計列由前端即時加總，不可手動輸入
- **三份清單（一館／二館／一館+二館）各自獨立編輯與存檔**，不會互相連動
- 「一館+二館」的目標資料 = 兩館加總

### 2.2 房間數級距（四捨五入）

```
bracketOf(rooms) = clamp(round(rooms / 5) * 5, 5, 30)
```

| 房間數 | 級距 |
|---|---|
| 0～2 | 5 |
| 3、4 | 5 |
| 7 | 5 |
| 8 | 10 |
| 13 | 15 |
| 18 | 20 |
| 23 | 25 |
| 28 | 30 |
| 40 以上 | 30 |

### 2.3 建議道數表

| 級距 | 肉 | 菜 | 蛋 | 小菜 | 炸物 | 滷菜 | 水果 | 甜點 |
|---|---|---|---|---|---|---|---|---|
| 5 | 1 | 1 | 1 | 3 | 1 | 0 | 2 | 1 |
| 10 | 1 | 2 | 1 | 3 | 1 | 1 | 2 | 1 |
| 15 | 1 | 3 | 1 | 3 | 2 | 1 | 3 | 1 |
| 20 | 1 | 4 | 1 | 3 | 3 | 1 | 4 | 2 |
| 25 | 1 | 4 | 1 | 3 | 3 | 2 | 5 | 2 |
| 30 以上 | 1 | 4 | 1 | 3 | 3 | 2 | 6 | 3 |

規則：

- 道數**只是參考**，顯示在菜色區頂端與各類別的「參考 N」
- 實際要出什麼**完全由勾選決定**，勾多勾少都不會報錯、不會被系統改動
- 每道勾選的菜**不需要填份量**，只要勾選
- 30 間以上菜色種類同 25 間（份量本來就沒有數字，不需要縮放）

### 2.4 備料區（飯／粥／茶葉蛋）

沿用 `房號與早餐` 的係數預設，可修改並存檔：

| 項 | 公式 | 預設係數 |
|---|---|---|
| 飯 | `大人 × riceAdult + 小孩 × riceChild` | 0.2 / 0.1 |
| 粥 | `大人 × porridgeAdult + 小孩 × porridgeChild` | 0.2 / 0.1 |
| 茶葉蛋 | `總人數 × eggRatio − eggStock + eggReserveCount + (總人數 × eggRatio) × eggReservePct / 100` | eggRatio 1.5、eggStock 0、eggReserveCount 0、eggReservePct 0 |

- `小孩 = 孩童 + 嬰幼兒`
- 飯、粥保留 1 位小數；茶葉蛋取整數
- 每項顯示 `base ＋ [額外增加] ＝ 合計`，額外增加為**當日手填**的非負整數，存於 `prep.{rice|porridge|egg}.extra`
- 命名界線：設定檔的 `eggReserveCount` 是「長期設定的預留顆數」，`prep.egg.extra` 是「當日臨時加的顆數」，兩者相加後才是最終茶葉蛋數
- 備料區可另外「新增備料」（自訂項：名稱＋數量，可勾選、可刪除）

### 2.5 牛奶飲料補貨（提醒）

- 依「用餐時段」列出補貨清單，**每日一份，三個目標共用**
- 每個時段顯示 `牛奶 × N` 與 `鋁箔包 × N`，預設 `1` 與 `12`，**每時段可自行修改數量**
- 每個時段可勾選「已補貨」
- 合計 = 各時段數量加總
- 用餐時段預設 5 個：`08:00 08:30 09:00 09:30 10:00`，可新增／刪除／啟用停用，存檔

### 2.6 多備菜色

- 與「當天出品」**不互斥**，同一道菜可以兩邊都勾
- 勾選頁顯示**全部**菜色，頁面下半有「多備（加菜）」區
- 顯示在當日頁「多備菜色」一行

### 2.7 冰箱庫存菜

- **全域一份勾選清單**（不隨日期變動）
- 勾選 = 冰箱裡**有這個料**（沒煮過的生鮮：青菜、雞豬牛魚）
- 未勾 = 沒有，去市場買菜時就是「要補齊」的項目
- 顯示 `✅ 冰箱有 N 項` / `🛒 要買 M 項`
- 可新增品項、填數量、刪除
- 品項是「沒煮過的生鮮」，與「煮好的食材」分開，不與備料區的計算連動

### 2.8 登入與權限

| 項目 | 決定 |

| 登入方式 | Firebase Auth Email＋密碼 |

## 3. 架構

```
瀏覽器
 ├── POST /api/fz/login  ──► Cloud Functions「fzapi」（Express, Node 22）
 │                           ├─ 檢查 fz_login_attempts 鎖定
 │                           ├─ POST identitytoolkit REST 驗證帳密
 │                           ├─ 檢查 fz_accounts.disabled
 │                           └─ createCustomToken → 回 { customToken, role, account }
 │                                    │
 │  signInWithCustomToken(token) ──────┼──► Firebase Auth（建立使用者工作階段）
 │                                     │
 ├── Firestore SDK ───────────────────┴──► Firestore（每日資料、設定、冰箱清單）
                                                ▲
 Cloud Functions「fzapi」──Admin SDK────────────┘（帳號管理）
```

**每日資料走 Firestore 直寫**（勾選與數字調整都必須毫秒級回應），**帳號與登入驗證走 Cloud Function**（需要 Rate limit、鎖定、停用判斷與 Admin SDK）。

`firebase.json` 的 hosting 需要 rewrite：`/api/**` → function `fzapi`。Function 名稱必須是 `fzapi`，不可用 `api`（`後台帳號管理` 已占用 `api`）。

### 3.1 登入為什麼不由前端 SDK 直接驗證

若前端直接呼叫 `signInWithEmailAndPassword`，密碼驗證完全發生在 Firebase 端，**Functions 無從得知「這一次登入失敗了」**，因此：

- 鎖定機制（失敗允許 5 次、第 6 次鎖 15 分鐘）無法實作
- 無法在使用者輸入密碼**之前**就回應「此帳號已停用」（停用者的 ID token 效期最長 1 小時）

所以登入流程整個搬進 Functions，用官方 REST 端點驗證：

```
POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key={API_KEY}
{ "email": "wind@fzbf.app", "password": "000000", "returnSecureToken": true }
```

- 成功 → REST 回 `localId`，Functions 查 `fz_accounts/{localId}` 拿 `role`
- 失敗 → REST 回 `INVALID_PASSWORD` / `EMAIL_NOT_FOUND` / `USER_DISABLED`，Functions 遞增失敗次數

驗證成功後 **不**把 REST 回傳的 `idToken` 交給前端（瀏覽器端 SDK 沒有 `signInWithIdToken`，交回去也建不了工作階段）。改為 `auth.createCustomToken(uid, { role, account })` 簽發 **custom token**，前端用 `signInWithCustomToken()` 建立工作階段——這是瀏覽器端唯一能消費伺服器簽發 token 的官方 API。

完整流程：

```
前端                            Functions                        Firebase Auth
 │ POST /api/fz/login            │                                  │
 │ {account, password} ─────────►│                                  │
 │                               │ 1. fz_login_attempts 鎖定檢查     │
 │                               │ 2. accounts:signInWithPassword ──►│
 │                               │ 3. 失敗 → count++；>5 則寫       │
 │                               │      lockedUntil = now + 15min   │
 │                               │ 4. 成功 → 查 fz_accounts 確認     │
 │                               │      未被停用、取出 role          │
 │                               │ 5. createCustomToken(claims) ────►│
 │◄────── { customToken, role, account } ───────────────────────────────│
 │ signInWithCustomToken(token) ────────────────────────────────────►  │
 │◄────── 使用者工作階段（ID token，Firestore rules 可驗證）─────────────│
```

`createCustomToken` 的 claim 帶 `{ role, account }`，讓 rules 可直接用 `request.auth.token.role` 判斷，減少文件讀取。`disabled` 仍以 `fz_accounts` 為準（見第 5 節）。

### 3.2 Firebase 設定需求

- Authentication → Sign-in method → **Email/Password 啟用**
- 專案 Web API Key 寫在 `functions/index.js` 的常數（公開資訊，非機密）
- `opencode-sk` 需已啟用 Blaze（Functions 必要條件，`後台帳號管理` 已在此專案部署 Functions，應已具備）

## 4. 資料結構

### 4.1 Firestore 集合（前置詞 `fz_`）

```
fz_accounts/{uid}    { account, role:'owner'|'staff', disabled,
                       mustChangePassword, createdAt, createdBy, updatedAt, updatedBy }
fz_config/app        { dishLib, prep, slots, updatedAt, updatedBy }
fz_pantry/pantry{ items:[{ id, name, inFridge, qty, note }], updatedAt, updatedBy }
fz_days/{YYYY-MM-DD} {
  head:   { b1:{ rooms, adult, child, infant }, b2:{...} },
  dishes: { b1:{ meat, veg, egg, side, fry, braise, fruit, dessert },
            b2:{...}, all:{...} },
  extra:  { b1:[], b2:[], all:[] },
  prep:   { rice:{ extra }, porridge:{ extra }, egg:{ extra },
            custom:[ { id, name, qty, done } ] },
  drinks: { [slotId]: { milk, foil, done } },
  updatedAt, updatedBy
}
fz_login_attempts/{account} { count, lockedUntil }
```

`fz_login_attempts` 只由 Cloud Functions 寫入，Client 不得讀寫。

### 4.2 `dishes.{target}` 與 `extra` 的內容

分類鍵一律用英文 key（`menu-lib.js` 的 `CATEGORIES` 定義），值是**菜名字串陣列**（非 id），`dishLib` 亦為 `{ [categoryKey]: string[] }`。

```js
// dishes：各分類勾選的菜色名稱
dishes: {
  meat:    ['滷豬耳', '豬腳'],
  veg:     ['地瓜葉', '絲瓜'],
  egg:     ['番茄蛋'],
  side:    ['涼拌海帶', '豆芽', '醬瓜'],
  fry:     ['炸芋頭'],
  braise:  [],          // 空陣列 = 尚未勾選
  fruit:   ['蘋果', '香蕉', '柳橙'],
  dessert: ['饅頭'],
}

// extra：多備菜色（與 dishes 不互斥），依目標分開存
extra: {
  b1: ['控肉'],
  b2: [],
  all: [],
}

// prep：備料區（依當日目標合併存放，base 不入庫）
prep: {
  rice:     { extra: 2 },   // base 由 prepBase() 即時算，不存
  porridge: { extra: 0 },
  egg:      { extra: 0 },
  custom:   [ { id, name, qty, done } ]  // 自訂備料項
}
```

### 4.3 設定內容

```js
fz_config/app = {
  dishLib: {
    meat:    ['滷豬耳', ...],
    veg:     [...], egg: [...], side: [...], fry: [...], braise: [...],
    fruit:   [...], dessert: [...]
  },
  prep: { riceAdult:0.2, riceChild:0.1,
          porridgeAdult:0.2, porridgeChild:0.1,
          eggRatio:1.5, eggStock:0, eggReserveCount:0, eggReservePct:0 },
  slots: [ { id:'s0800', label:'08:00', enabled:true, milk:1, foil:12 }, ... ]   // 預設 5 個
}
```

每個時段自帶 `milk`（牛奶）與 `foil`（鋁箔包）數量；`drinkTotals(slots, cfg, state)` 的 `cfg` 為可選覆寫，未提供時以 `milkPerSlot:1` / `foilPerSlot:12` 為預設（原名 `cansPerSlot` 一律改稱 `foilPerSlot`）。

`dishLib` 的分類鍵固定為八個：`meat veg egg side fry braise fruit dessert`（顯示名稱為 `肉 菜 蛋 小菜 炸物 滷菜 水果 甜點`，定義在 `menu-lib.js` 的 `CATEGORIES`）。**沒有冷門分類的自訂機制**（使用者需求未提及，YAGNI）。

## 5. Security Rules

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function acct() {
      return get(/databases/$(database)/documents/fz_accounts/$(request.auth.uid));
    }
    function active() {
      return request.auth != null
          && exists(/databases/$(database)/documents/fz_accounts/$(request.auth.uid))
          && acct().data.disabled == false;
    }
    function isOwner() {
      // 停用判斷以 fz_accounts 為準（custom claim 在停用後最長 1 小時仍有效）
      return active() && acct().data.role == 'owner';
    }

    // 帳號只能由 Cloud Functions（Admin SDK）寫入
    match /fz_accounts/{uid} {
      allow read:  if active() && (request.auth.uid == uid || isOwner());
      allow write: if false;
    }
    match /fz_login_attempts/{a} { allow read, write: if false; }

    match /fz_days/{date}   { allow read, write: if active(); }
    match /fz_pantry/pantry { allow read, write: if active(); }

    match /fz_config/app {
      allow read:   if active();
      // 菜色庫人人可加；其餘設定僅主帳號
      allow create: if isOwner();
      allow update: if isOwner()
        || request.resource.data.diff(resource.data).affectedKeys()
             .hasOnly(['dishLib', 'updatedAt', 'updatedBy']);
      allow delete: if false;
    }

    match /{document=**} { allow read, write: if false; }
  }
}
```

要點：

1. **不使用 `if true`**
2. `fz_accounts` 寫入全面禁止，只有 Admin SDK 能動
3. `active()` 讀 `fz_accounts/{uid}.disabled`，補上「Firebase Auth 停用後 ID token 仍有 1 小時效期」的漏洞
4. `fz_config/app` 用 `diff().affectedKeys()` 讓菜色庫人人可加、係數與時段只有主帳號能改

## 6. Cloud Functions 端點（function 名稱 `fzapi`）

| 方法 | 路徑 | 權限 | 說明 |
|---|---|---|---|
| POST | `/api/fz/login` | 公開（rate limit） | `{ account, password }` → 內部 `emailOf(account)` 組 email、REST 驗證密碼、鎖定檢查、停用檢查 → 回 `{ customToken, role, account, uid }` |
| GET | `/api/fz/me` | 登入者 | 回 `{ uid, account, role }`（前端啟動時取得角色；停用者在此被擋） |
| POST | `/api/fz/change-password` | 登入者 | `{ currentPassword, newPassword }` 改自己，需以 REST 驗證舊密碼 |
| GET | `/api/fz/accounts` | owner | 帳號清單（不含任何密碼資訊） |
| POST | `/api/fz/accounts` | owner | `{ account, password }` → `auth.createUser` ＋ 建立 `fz_accounts` |
| PUT | `/api/fz/accounts/:uid` | owner | 改密碼 / 停用啟用 / 改角色；不可停用或降級自己 |
| DELETE | `/api/fz/accounts/:uid` | owner | 刪除帳號；不可刪自己、不可刪最後一個 owner |

實作要點：

- 密碼只交給 Firebase Auth（bcrypt 雜湊），**Firestore 不存任何密碼**；Functions 端一律以 REST `accounts:signInWithPassword` 驗證舊密碼
- 建立帳號時 email 由 `account + '@fzbf.app'` 組成
- 密碼規則：長度 6–72 字元（Firebase 上限），最少 6 碼
- 停用帳號：`auth.updateUser(uid, { disabled: true })` ＋ 更新 `fz_accounts.disabled`（兩者都要做，見第 5 節）
- `login` 失敗遞增 `fz_login_attempts/{account}.count`；允許 5 次失敗，第 6 次（`count > 5`）寫 `lockedUntil = now + 15min` 並回剩餘分鐘；成功登入則清除該筆紀錄
- 受保護端點 `verifyToken` 用 `auth.verifyIdToken(token, true)`（檢查撤銷）
- `isOwnerReq` 中介層：`verifyToken` 後讀 `fz_accounts/{uid}` 判斷 `role === 'owner' && !disabled`
- Express rate limit：`/api/fz/login` 15 分鐘 20 次、其餘 `/api/fz/*` 15 分鐘 200 次
- 不記錄任何密碼到 console / audit log

## 7. 核心純函式（`core.js`，Node 直接 `require` 測試）

沿用 `房號與早餐` 的 `core.js` 模式：UMD 包裝，瀏覽器掛 `window.FZCore`，Node `require('./core.js')`。

| 函式 | 輸入 | 輸出 |
|---|---|---|
| `bracketOf(rooms)` | `number` | `5｜10｜15｜20｜25｜30` |
| `suggestDishes(rooms)` | `number` | `{ 肉, 菜, 蛋, 小菜, 炸物, 滷菜 }` |
| `suggestFruitDessert(rooms)` | `number` | `{ fruit, dessert }` |
| `peopleSum(b1, b2)` | 兩個 head | `{ rooms, adult, child, infant, kid, total }` |
| `peopleFor(target, b1, b2)` | `'b1'｜'b2'｜'all'` | 同上 |
| `prepBase(target, cfg, day)` | `'b1'｜'b2'｜'all'` ＋備料係數 ＋`{ b1, b2 }` | `{ head, rice, porridge, egg }`（base 值） |
| `prepLine(base, extra)` | 基準量 ＋ 額外量 | `{ base, extra, total }`，`extra` 負數夾為 0 |
| `drinkTotals(slots, cfg, state)` | 時段陣列＋可選覆寫＋當日狀態 | `{ rows, milk, foil, pendingMilk, pendingFoil }` |
| `summaryLine(items)` | 名稱字串陣列 | `'滷豬耳、控肉'`，空則 `'（未選）'` |
| `pantrySplit(items)` | 冰箱品項 | `{ has:[], buy:[] }` |
| `weekOf(anchorKey)` | `'YYYY-MM-DD'` | 7 個日期字串 |
| `dateKey(d)` / `fmtDate(key)` | Date / 字串 | 本地日期字串 / `'10/04（週日）'` |
| `emailOf(account)` | `'wind'` | `'wind@fzbf.app'` |

規則細節：

- `bracketOf(NaN｜負數｜undefined)` → `5`
- `prepBase` 的 `head.total` 為 0 時三項皆為 0
- `prepBase` 的 egg 結果不允許負數（`Math.max(0, …)`）
- `prepBase` 的 `cfg` 若某係數為 `null`／`undefined`／空字串／`NaN`／無限大，視為**未設定**，該係數改用 `DEFAULT_PREP`（不可被 0 蓋掉，否則飯／粥／蛋會靜默歸零）
- `prepLine` 回傳物件而非數值；`extra` 負數夾為 0
- `summaryLine` 略過空字串；若結果為空則回 `'（未選）'`（不做菜色庫過濾）
- `dateKey` 使用**本地時間**，不使用 `toISOString()`（會時區偏移）
- `weekOf` 跨月正確（`10/30 → 11/05`）

## 8. 頁面與流程

### 8.1 登入牆

- 未登入只顯示登入頁，`#loginView`
- 帳號欄 placeholder `例：wind`；密碼欄下方灰字 `密碼最少 6 碼`
- 密碼欄附顯示／隱藏切換鈕（依專案規範）
- 錯誤訊息區：帳密錯誤／帳號已停用／已鎖住，剩餘幾分鐘／嘗試過於頻繁
- **無註冊入口**

### 8.2 日曆主頁

- 月曆，今天紅框反白
- 有資料的日期顯示圓點
- 點任一日期 → 設為錨點，下方顯示「錨點日 ～ 錨點日+6」共 7 天
- 七天頁籤橫向捲動，每格顯示日期、房間數、有無圓點；今天加 ⭕
- 錨點預設為今天；`‹ 本週 ›` 切換前後 7 天

### 8.3 當日頁

順序（自上而下）：

1. 頂部列：`‹ 日期 今日 ⭕ 匯出 ☰`
2. **入住統計**：一館／二館各四個數字欄（房間／大人／小孩／嬰幼兒），`−`/`+` 快速按鈕；合計列唯讀
3. **吸頂三顆按鈕**：一館／二館／一館+二館（捲動時 `position: sticky`）
4. **參考列**：`23 間參考｜菜色 肉1 菜4 蛋1 小菜3 炸物3 滷菜2｜水果5 甜點2`
5. **菜色區**（緊湊清單式，六類）：每類一行 = 彩色標籤 + `已選 N · 參考 M` + 換行的菜名 + 右邊 `›`
6. **水果／甜點**兩行
7. **多備菜色**一行
8. **備料區**（藍標籤）：飯／粥／茶葉蛋各 `☐ base ＋[extra] ＝ total`，加自訂項與「＋新增備料」
9. **牛奶飲料補貨**（靛標籤）：逐時段 `☐ 時段 牛奶[1] 鋁箔包[12]`，下方合計
10. **冰箱庫存菜**（灰標籤）：`✅ 冰箱有 N 項　🛒 要買 M 項 ›`

### 8.4 勾選頁

- 點任一類別的 `›` 進入
- 頂部 `已選 N 道`
- 中段：該分類全部菜色 checkbox 長清單（不摺疊）
- 下段：`多備（加菜）` 區，同樣是全部菜色，可與中段重複勾
- 底部：`全選` / `清除` / `儲存`（儲存後關閉並刷新主畫面）
- 勾選狀態在**開啟時就寫入 Firestore**（debounce 800ms），不需等按儲存；`儲存` 只是關閉

### 8.5 設定頁

| 項目 | 權限 | 內容 |
|---|---|---|
| 菜色庫管理 | 所有登入者 | 八個分類分頁，可新增／改名／刪除／排序 |
| 冰箱庫存品項 | 所有登入者 | 品項增刪、勾選（在Fridge）、數量、備註 |
| 用餐時段 | owner | 新增／刪除／啟用停用／改名 |
| 備料係數 | owner | 飯粥四係數、茶葉蛋四參數 |
| 補貨量預設 | owner | 牛奶／鋁箔包預設值 |
| 帳號管理 | owner | 帳號清單、停用、刪除、建立員工 |
| 變更我的密碼 | 登入者 | 需舊密碼 |
| 登出 | 登入者 | |

### 8.6 CSV 匯出

匯出「錨點日 7 天 × 3 個目標」的完整內容，UTF-8 BOM，欄位：

```
日期, 目標, 房間數, 大人, 小孩, 嬰幼兒,
```

檔名：`風自然早餐_YYYYMMDD-YYYYMMDD.csv`

## 13. 已知取捨

1. **停用帳號有最長 1 小時的殘留視窗**：Firebase Auth 停用後，已簽發的 ID token 在效期內仍可讀 Firestore。由 `active()` 讀 `fz_accounts.disabled` 來堵住——因為停用時 Functions 會同步更新該欄位，所以最多只有兩次請求的落差，可接受。
2. **`fz_config/app` 是單一文件**：菜色庫若成長到數百項，整份讀寫會變重。目前估算 8 類 × 20 項 ≈ 3KB，遠低於 1MB 上限。成長到需要拆分時再說。
3. **勾選即時寫入 + debounce 800ms**：連續勾多項時可能丟失最後一次變更。實作時確保 debounce 結束後一定觸發最後一次 flush。
4. **`base` 不入庫**：改了係數之後，歷史日期的備料區 base 會跟著變。若需要「鎖定當時係數」，要改成把 base 一起存。目前不做，因為係數是長期固定的。
5. **沒有稽核日誌**：不同於 `後台帳號管理`（有 `auditLogs`），本專案不記錄誰改了哪一筆資料。資料為廚房作業性質，非個人隱私，暫不做。若日後需要再補。
6. **`createCustomToken` 依賴 Identity Toolkit REST 可用性**：`accounts:signInWithPassword` 是 Google 官方公開端點，但非 SDK 保證契約。若未來失效，替代方案是改回前端 `signInWithEmailAndPassword` ＋ 犧牲登入鎖定功能。實作階段（階段 1）會先實測確認此端點可用。
7. **鎖定以 email 為鍵**：`fz_login_attempts/{email}`。同一個人若從不同 email 嘗試不會被鎖；反過來鎖定只影響該 email，不影響其他帳號。符合直覺。
8. **`@fzbf.app` 是虛構網域**：Firebase Auth 不驗證網域擁有一致性，因此不需要真的擁有 `fzbf.app`。好處是登入畫面只需輸入 `wind` 而非完整 email。
